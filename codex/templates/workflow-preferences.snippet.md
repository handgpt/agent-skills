## Personal workflow preferences

These preferences supplement the host's instructions; they do not replace its
security boundaries, authorization rules, or mandatory verification.

- Follow through on authorized work. Resolve routine reversible choices with context; ask when missing information materially changes the requested outcome. Do not duplicate approvals already granted for the same scope.
- Keep all work within the agreed outcome. Defer newly discovered features or enhancements that were not established in the conversation and would add unexpected work, including optional backward-compatibility layers, migration helpers, fallback paths, and adjacent improvements. This does not authorize breaking required existing interfaces or omitting prerequisites for the agreed result. If such a dependency prevents completion, explain it and resolve the scope with the user before claiming completion or taking a dependent consequential action.
- Complete the authorized scope and briefly list concrete deferred items in the final response, with their benefit and the consequence of omission, so the user can decide whether to add a follow-up version. Do not implement these additions preemptively or invent a speculative backlog; omit this list when nothing relevant was deferred.
- Use subagents for bounded, independent subtasks when delegation is available and useful alongside the main work. Give each a clear scope and expected result. Avoid delegation for trivial work, dependent steps, or concurrent edits to the same files; do not force a model or reasoning override without a task-specific reason.
- Prioritize fast implementation and economical use of time and tokens. Read only the test files or excerpts needed to understand the changed behavior or diagnose a concrete failure; do not scan entire test suites by default.
- Default to no new test code. Reuse the smallest relevant existing check when useful; low-risk changes may need no test execution. Unless the user requests detailed testing, limit new or expanded tests across the entire task to at most three focused cases, placed in the relevant modules' existing test files where possible, with minimal fixtures and no new test framework. This is a ceiling, not a target; do not delete existing tests to meet it.
- When agy review is performed, use its findings to target any remaining minimal validation. Do not routinely add extensive tests after review or turn generic coverage suggestions into extra work. Review is useful evidence, but does not prove runtime correctness or waive mandatory checks. Honor required checks and concrete material-risk validation; if these require exceeding the default test budget, keep the exception narrow and explain why.
- Reserve exhaustive suites, broad edge-case matrices, coverage targets, property/fuzz testing, and elaborate test scaffolding for an explicit user request for detailed testing, except where mandatory requirements apply. Stop once the necessary checks pass; expand or repeat only for new changes, failures, or unresolved material risks. Do not add tests that merely restate implementation.
- For documents, PDFs, and slides, preserve required final render and content checks. Batch related edits before rendering. Finish when content is correct, required elements and template fidelity are preserved, and there is no clipping, overlap, missing glyphs, or broken layout at normal viewing size. Fix observed defects; do not keep restyling a passing artifact in pursuit of undefined perfection.
- Prefer clear, concise writing. Punctuation, arrows, passive voice, or a particular title form are acceptable when they improve precision or follow the user's template; treat blanket style prohibitions as preferences, not correctness rules. Preserve requested titles and references.
- Follow the host's progress-update and skill-disclosure requirements, including when a visualization skill prefers silence. Keep updates brief and focused on outcomes.
